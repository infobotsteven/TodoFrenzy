# Data model

Polish version: [pl/MODEL-DANYCH.md](pl/MODEL-DANYCH.md).

SQLite (file `data/todo.db`, WAL mode, `foreign_keys = ON`, `busy_timeout = 5000`). The schema is in `server/src/db/schema.ts`
(Drizzle), migrations in `server/drizzle/`. Types returned by the API are in `shared/src/types.ts`.

```text
projects ──< checklists ──< tasks ──< task_users >── users
                 │
                 └──< checklist_tags >── tags
```

Deleting a project deletes its lists and tasks, deleting a list deletes its tasks, deleting a user/tag removes only the links
(`ON DELETE CASCADE`). In the code and the database a "list" is called `checklist`.

## Tables

### `projects`
| Column | Type | Notes |
|---|---|---|
| `id` | text PK | nanoid, 16 characters `[0-9a-z]` — also the "secret" in the link |
| `name`, `description` | text | name 1–200 characters, description up to 5000 |
| `color` | text null | a palette key (`red`…`gray`) or `brown` (reserved for "Other") |
| `is_system` | integer(bool) | `true` only for the permanent "Other" project (exactly one) |
| `archived_at` | integer (ms) null | when it was archived; `NULL` = active. Archiving a project = archiving its tasks (nothing is copied, tasks derive it from the project's `archived_at`) |
| `sort_order` | integer | explicit order |
| `created_at`, `updated_at` | integer (ms) | `updated_at` is also refreshed on changes to lists/tasks (`touchProject`) |

### `checklists` (lists)
`id`, `project_id` → projects (cascade), `name`, `description`, `color` (null), `sort_order`, timestamps.
Index `(project_id, sort_order)`. Lists **have no dates** (the `start_date`/`end_date` columns were removed in migration 0004).

### `tasks`
| Column | Type | Notes |
|---|---|---|
| `id` | text PK | |
| `checklist_id` | text → checklists (cascade) | |
| `name`, `description` | text | |
| `completed` | integer(bool) | |
| `completed_at` | integer (ms) null | when it was marked completed (the source of **statistics**); set once (marking completed again does not move it), cleared on unticking; a task created as completed gets "now". Copies of tasks are not completed |
| `priority` | text | `none` / `low` / `medium` / `high` (plain text — easy to extend without a migration; the set lives in `shared`) |
| `due_date` | text null | `YYYY-MM-DD` (one date, no time) |
| `sort_order` | integer | |
| `created_at`, `updated_at` | integer (ms) | |

Indexes: `(checklist_id, sort_order)`, `(due_date)` (calendar and overdue), `(completed_at)` (statistics).

### `tags`
`id`, `name` (unique; routes also compare case-insensitively). Tags belong to **lists** through `checklist_tags`.

### `users`
`id`, `nick` (unique case-insensitively — enforced by the route), `avatar` (a key from `AVATARS`), `created_at`.
No login — they are only "labels" to assign to tasks.

### `sessions`
Login sessions: `token_hash` (PK; **sha256 of the cookie token**, the token itself is not stored), `created_at`, `last_seen_at`, `expires_at` (indexed), `credential_fingerprint`
(a fingerprint of the login and password from `.env`; sessions with a different fingerprint are invalid and removed at startup — changing the password logs everyone out). Cleaned at startup and every hour.
This is the only login data in the database — the account's login and password are in `.env`, not in the database.

### `task_users` and `checklist_tags`
Join tables (composite key, index on the second column).

## Conventions

- **Time** in the database is unix ms (`integer timestamp_ms`), ISO 8601 in the API. **Task dates** are `YYYY-MM-DD` text (no time zones).
- **Order**: `sort_order` is explicit; a new item = `max + 1`; reordering "in slots" (see ARCHITECTURE). The first in the project
  list is always `is_system` (sorted `is_system desc, sort_order, created_at`).
- **Enums** (`COLORS`, `PRIORITIES`, `AVATARS`) live in `shared/src/types.ts`; columns are plain text with an `enum` type on the Drizzle side.
- **Validation** of input is Zod schemas in `shared/src/index.ts` (the frontend uses the same ones in forms).

## Migrations

Generated by `npm run db:generate` after changing `schema.ts`; applied automatically at server start (and manually with `npm run db:migrate`).
**Data-safety rules:** prefer additive migrations; before a migration that changes/deletes data run
`npm run db:backup` and try it on a copy of the database file (with a different `DATABASE_PATH`).

| # | File | What it does |
|---|---|---|

| 0001 | `lame_moonstone` | project and list colors |

## Backups

`npm run db:backup` uses the SQLite `backup` API (a consistent copy even while the server is running in WAL mode) and writes
`backups/todo-YYYYMMDD-HHMMSS.db` (`BACKUP_KEEP` are kept, default 14). To restore: stop the server and replace the file
`data/todo.db` (also delete `todo.db-wal` and `todo.db-shm`).
